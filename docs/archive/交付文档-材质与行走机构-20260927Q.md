## §1 坦克行走机构（履带花纹 + 侧面 + 负重轮）

### 1.1 病症（两条，都是实机可见）

1. **花纹位相错**：2026-09-26 A5 用"整张贴图转 90°"的**全局纹理矩阵**摆正侧面 —— 全局旋转治不了逐面需求：
   90° 让 ±X 侧成了竖条（对），但同一张矩阵把 ±Y 顶/底变成"沿车长走的条纹"、把 ±Z 前后断面变成
   2cm 一道的细密竖条。真实履带在这两个面上都应是**横跨履带宽度、沿环向排开**。
   第三人称看自己坦克时正对眼的就是履带的前后断面与顶面 —— 这就是"水平方向布置和运转"。
2. **侧面整片是履带**：履带盒的 ±X 面是行走机构的最外一层，铺着履带花纹；负重轮只比履带外凸 1cm，
   于是侧视图整条车下缘都是履带、轮子看不见 —— 用户二次实报"轮子侧面处仍有履带…不能是履带"。

### 1.2 修法（`js/15-vehicles.js`）

- **逐面烘焙 UV**（`trackBoxPrep`，替代 `treadBoxUV`）：花纹只出现在**履带环向的四个面**——
  ±Y 顶/底（接地段/回程段）、±Z 前/后断面（绕过主动轮/诱导轮那段）；花纹条永远横跨履带，
  变化方向永远沿环向，符号按"后置主动轮 + 前置诱导轮"取（前进时后端面向上滚、前端面向下滚）。
  纹理由此退出该链路（`repeat=1 / rotation=0`），`update()` 的 `offset.y += vel*dt/trackTileLen` 一字未动。
- **±X 侧面 = 装甲侧板（裙甲）**：履带盒改成**两段材质** `[履带贴图, M.tone]`；索引表重排成
  `[py,ny,pz,nz | px,nx]` 并写两组 groups ⇒ 一个 mesh 仍然只有 **2 段 draw call**（默认 6 组会渲染 6 次）。
  侧板保留 BoxGeometry 原始 0..1 面 UV ⇒ 与车体各面同一密度（`TEX.grime` 涂装板，不是履带花纹）。
- **负重轮外移**：新增 `tkSpec.whSx = trkSx + WH_OUT(0.06)`，轮外沿比侧板外沿凸 **7cm**（旧版 1cm）
  ⇒ 侧视图 = 侧板 + 一排明确凸出的负重轮。整车包围盒只被轮子撑宽 1cm，仍在 `verify-vehmodels` 的
  "halfW = 实测半宽 ±0.02" 容差内（该探针 10/0 全过）。
- **顺带修一处埋着的建模缺陷**：四号/黑豹的侧裙板（Schürzen）旧挂点 `hullW/2+0.42`（四号 = 1.73m）
  而履带箱外沿在 1.97m ⇒ 6 件分片**整片埋在履带箱里**，只露出一截。现挂到履带外沿 +3.5cm
  （裙板内面离侧板 5mm、外面在负重轮之内 5mm），与侧板同层成一套分片裙甲；包围盒不变。

### 1.3 实机核对

- 第三人称看自己坦克**尾部**：履带断面上的横档应**一道一道沿车高往上滚**（前进时）；倒车则反。
- 看**侧面**：是一块涂装钢板（随战役/涂装色的侧板）+ 一排凸出的负重轮；**看不到履带花纹铺在侧面**。
- 德系（四号/黑豹）：侧裙板分片应明显挂在履带外侧上方（旧版几乎看不见）。
- 开起来履带花纹的**滚动速度与地面零打滑**（每贴 1.5m 世界长，8 条/贴 ≈ 19cm 条距）。

### 1.4 判据

`dev/verify-tread-20260927.js`（新登记）**146 ✓ / 0 ✗**：真 three r152 + 真 `Tank.prototype.buildMesh`，
按"纹理矩阵 × 顶点 UV"算每个面四个角点的采样坐标，断言：

- ±Y/±Z 四面的采样 v 只是 z（顶底）或 y（前后）的函数，另两轴偏导为 0（横齿横跨、沿环向排开）；
- ±X 侧面 **dv/dz = 0**、UV 仍是原始 0..1、材质挂在 `materialIndex=1`（= `M.tone`，不带履带贴图）；
- 前后断面 dv/dy 符号相反且 |dv/dy| = 1/每贴；顶/底 dv/dz 符号相反；条距 15~24cm；
- 负重轮外沿 = 整车最宽点且 > 履带箱外沿 + 5cm；轮心 = `whSx`；两侧共用同一几何；恰好 2 段 groups；
- 裙板挂点落在"侧板之外、负重轮之内"（并记录旧挂点确实埋在里面）；
- **阴性对照**：旧写法（原始盒 UV + `repeat(1,N)` + `rotation=π/2`）必须让"前后断面沿车宽排开"与
  "侧面 v 随 z 变"两条判据报红 ⇒ 判据不是空转。
- `verify-animfix-20260926` 的第 15 条判据随机制改写（源码防回退 + 阴性对照锚点一并更新，37/0）。

## §2 建筑材质（严重的材质不一致）

### 2.1 病症（三条可量化）

1. **逐块色相乱跳**：砖/石/木/瓦的逐块颜色写成 `rgb(randi(),randi(),randi())` —— 三通道**各抖各的**。
   实测 `TEX.stone` 的逐块色相跨度 **13°~156°**（同一堵墙上"粉石"挨着"青石" = 拼色马赛克）；
   brick 12~39° / wood 20~60°（橄榄 ↔ 红木）/ roof 16~40°。
2. **平铺缝上的硬伤**：抹灰贴图里画到画布**外面**的返潮斑在对边没有副本（缝上是半个渐变斑），
   墙脚还有一条 `y=212..256` 的**硬边**半透明带 —— 平铺到墙上是每 1.8m 一道明暗台阶（"坏块感"的第二个来源）。
   砖的 pre-roll 半块单独随机 ⇒ 缝两侧的同一块砖**颜色不一样**。
3. **帆布密度漂移**：`TEX.cloth` 没登记 `UV_DENSITY` ⇒ 一张 128px 白噪帆布按"六面 0..1"铺：
   同一顶帐篷上 2.8m 坡板与 0.5m 檐口相差 **17.1×**（实测 0.20~3.47 m/贴，78 件/468 面）。

### 2.2 修法（`js/02-scene.js` + `js/00-config.js` + `js/05a-buildings.js`）

- **逐块色抖单源 `shade(base,k,w)`**：只抖**明度**（三通道乘同一系数 k∈0.86~1.14），再给一点同向暖冷偏移
  （ΔR=−ΔB，±4）。覆盖同一亮度包线 ⇒ 观感不变，色相不再跨档。落到 stone / brick / wood / woodDark /
  roof / 砂袋碎屑 / 苔痕 的 **Canvas 兜底版与 SVG 精修版两边**（浏览器看的是 SVG 那一边）。
- **平铺闭合**：新增 `wrapOffs()` —— 元素越出画布时在对边补等价副本（抹灰返潮斑、裂纹、木纹线）；
  形状放 `d` 里保持**逐字相同**、位置走 `transform` ⇒ 缝上是同一个图案的两段，不是"断头"。
  砖改成**列色表**（4 列 × 64px = 256 ⇒ 左右缘半砖取同列色）；石/砖/木/瓦的网格周期与贴图对齐
  （石/砖 32px 行高 ×8、木 8 板 ×32、瓦 8×8）。
- **接缝连续**：抹灰墙脚返潮带改成**两端都归零**的竖向渐变（上下缘透明 ⇒ 平铺零台阶），删掉硬边矩形。
- **帆布密度归一**：`UV_DENSITY` 补登 `cloth:1.6`（与 plaster/earth 同档），`05a` 的
  `tentMatA/tentMatB` 挂 `uvRef` ⇒ 坡板/檐口/山墙同一把尺。

### 2.3 实机核对

- 走到**石砌建筑**（教堂/石塔/石墙）前：整堵墙应是同一族灰，不再出现"一块粉一块青"的拼色；
  走近看砖墙：相邻砖深浅有别但**同色相**；木墙/木栅栏不再"一块橄榄绿一块红木"。
- **抹灰墙**（白灰墙）：上下不应有每 1.8m 一道的横向明暗线；返潮斑不应在缝上被切成半个。
- **帐篷**：坡顶帆布与檐口、山墙的织纹粗细应一致（旧版坡顶被拉成粗布、檐口细得像砂纸）。
- 屋顶瓦片：色相统一（同一族赭红），仍是逐片深浅不一的瓦。

### 2.4 判据

`dev/verify-matseam-20260927.js`（新登记）**42 ✓ / 0 ✗**：

- ① **色相一致性**：直接读 Canvas 兜底版的**绘制调用**（录制版 2D 上下文）与 SVG 精修版的填充色，
  对"砌块/板条"这一类颜色算色相（环形最小弧）⇒ 断言 ≤20°，同时断言**明度极差 ≥8%**
  （证明收敛的是色相、不是把贴图抹平）。实测 stone 12.1°/10.5°、brick 2.2°/1.9°、wood 1.2°/0.6°、
  woodDark 1.5°/2.7°、roof 5.0°/5.4°；明度极差 15~27%。
- ② **平铺闭合**：解析 SVG 元素 ⇒ 越出本格的元素必须在 ±W/±H 平移处有**同形副本**
  （brick/plaster/stone/wood/woodDark/roof/sandbag/cloth/grime 全部闭合）。
- ③ **接缝连续**：横跨整幅的**部分高度**条带必须自己在 y 上首尾相接铺满 0..H（竖条同理）。
- ④ **帆布密度**：真 three + 全脚本链建柏林世界 ⇒ 468 个帆布盒面的密度跨度 **1.00×**（旧版 17.1×）、
  中位 1.60 = `UV_DENSITY.cloth`。
- ⑤ **阴性对照**：旧写法的硬边返潮带 ⇒ ③ 报红；缺口斑块 ⇒ ② 报红；补上对边副本后立刻转绿。
- `dev/verify-svgtex.js`（既有）40 个生成器 XML/引用/平铺域校验全过。

## §3 观战模式结算判定（选了又取消 → 不该判成观战局）

### 3.1 病症

`player.specUsed` 在**兵种卡上点开开关那一刻**就盖章，且**永不回退** ⇒ "点开 → 再取消"照样把整局判成
观战局、不进历史记录（用户实报）。粘性标记本身的意图（防"开观战刷完再关"）要保，但盖章点太早。

### 3.2 修法（判据收窄到"**在观战态下部署过**"）

- **唯一盖章点**收进 `23-deploy.deployPlayer()`：`if(p.spectator) p.specUsed=true;`
  （落点在 `specWant → spectator` 的意图结算之后）⇒ 只有"顶着观战态真的进了战场"才算。
- `22-hud` 的兵种卡开关**不再**盖 `specUsed`；确认框与游戏说明文案同步改写
  （"下一次部署才生效；生效后本局不计入历史记录 —— 只点开开关又取消的不算"），中英双语同步。
- `21-match` 结算判据仍是 `counted = !player.spectator && !player.specUsed`（粘性保留）：
  开观战刷完再关的局**照旧**不进历史；只点开关又取消的局**正常**进历史。

### 3.3 实机核对

- 兵种卡上点开观战开关 → 再点一次取消 → 打完这一局：结算页应照常把这局计入历史记录
  （数据面板的历史战绩/本图记录照常更新）。
- 点开开关并在**下一次部署**时以观战者身份进战场（有"观战待生效/观战中"标记）→ 结算页与数据面板
  应写明"本局不计入历史记录"。
