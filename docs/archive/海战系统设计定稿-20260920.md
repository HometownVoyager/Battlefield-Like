## 一、格局：为什么塔拉瓦的玩法骨架是"剖面算出来的"

塔拉瓦环礁已具备（2026-09-18/19 批建好的场地，本批**不新增地形**）：

- **四面环海孤岛**：海面占图 67%、可通航深水（>2.5m）50%；四条岸线首尾相接成闭合环，无一处陆地接图缘。
- **四湾四岬**：南登陆湾 / 西湾 / 东湾 / 北湾 四个可上陆滩头；四个岬角是防御制高点（灯塔 / 岸炮台 / 观察哨）。四湾各配一组进近航道浮标（`sea.lanes`）。
- **环岛通航环带** `sea.navRing` d=43..200（水深 3.4→13m）：绕岛一周不断 ⇒ 艇可绕岛机动、择湾逼近。
- **长栈桥泊位** `sea.berths`（水深 ≈3.1m）：艇的靠泊位。
- **切深航道** `sea.channels`（下切到 2.45m）：两条冲南湾的深水走廊。

### 1.1 离岸剖面 = 天然的载具分工（不需要额外规则）

`CAMPAIGN.sea` 的离岸剖面（`shelf → reef → edge → slope → basin`）算出的水深。
下表**不是估算，是 `dev/_probe-config.js` 实算出来的**（Lead 已跑通验证）：

| 剖面带 | 离岸距离 d | 水深 | PT 艇（吃水 0.95m） | 两栖车（吃水 0.40m / wadeDepth 0.55m） |
|---|---|---|---|---|
| 冲滩带 | 0→22m | 0 → 1.221m | **d < 17.15m 硬搁浅** | d < 7.25m 履带态（压地走，不判搁浅） |
| 　└ 浮航切换 | d≈9.9m | 0.55m | — | **履带态 → 浮航态** |
| 礁盘平台 | 22→36m | 1.221 ~ 1.277m | 浮航，吃浅水减速 | 浮航，畅通 |
| 礁缘陡坎 | 36→43m | 1.221 → 3.321m | 自由 | 自由 |
| 外坡 | 43→80m | 3.4 → 6.9m | 全速区 | 浮航 |
| 海盆 | >80m | 7.0 → 13m | 全速区 | 浮航 |

**关键推论（可当断言用）**：浮航态的前提是 `depth ≥ wadeDepth(0.55) > draft0(0.40)` ⇒ **两栖车在 `flood=0` 时永远不可能硬搁浅**（"两栖车搁浅"只可能发生在进水之后）。PT 艇则恒浮航态，其 **17.15m 硬搁浅线就是设计意图的核心**。

**这正是史实塔拉瓦的格局**：两栖车冲上沙滩，艇停在礁盘外做火力支援。规则不是"规定的"，是从剖面里算出来的。

> **实现纪律**：载具的水深判定只能走现有单源接口 `waterYAt / waterDepthAt / inSea / inDeepWater`（03-terrain）。
> **严禁**在本批任何新文件里再写一套岸线/水深算术（纲领 §4.3）。

- **鱼雷**：对艇武器。命中即重创（`flood` 大幅跳增）；对岸无效（水下引信，撞滩哑火）。

## 三、四档物理（用户选"中等档"）

### 3.1 吃水（draft）
```
draft = spec.draft0 + flood * 0.5          // flood ∈ [0,1]，进水越多吃水越深
hullY  = waterYAt(x,z) - draft             // 船体世界高（浮力自动贴合水面）
```
- 水面以下部分按 `draft` 截断可见（水线渲染）；浅水/搁浅时船体会"坐"在泥面上。

### 3.2 浮态（attitude）
| 项 | 公式 | 说明 |
|---|---|---|
| 转向横倾 | `roll → -yawRate * k_roll`（阻尼弹簧，回正） | 转弯时船体向外侧倾 |
| 加速纵倾 | `pitch → -accel * k_pitch`（阻尼弹簧） | 起步抬头、刹车埋首 |
| **浪涌** | `y += sin(nowT * 1.3 + x*0.05 + z*0.03) * 0.15` | **与现有浮标 `BUOYS` 同源相位口径**（05b），保证艇与浮标同波 |

### 3.3 搁浅（grounding）
```
d = waterDepthAt(x,z)
if (d < draft)              → 硬搁浅：速度阻尼到 0，可倒车脱困（倒车推力 0.6×）
else if (d < draft + 0.45)  → 浅水：速度 ×0.40，每秒刮擦伤害 4（龙骨擦礁）
```
- PT 艇 `draft0 = 0.95` ⇒ 冲滩带 d<17m 处搁浅；礁盘（1.22m）能过但吃浅水减速。
- 两栖车 `draft0 = 0.40` ⇒ 礁盘畅通，可一直开到冲滩带再转履带。

### 3.4 进水与沉没（flood / sink）
```
受击 → flood += dmg * spec.floodK     // floodK: 艇大、两栖车小
flood > 1 → state = 'sinking'
  ① 0.8s 倾斜（roll 渐增、速度衰减）
  ② 3~6s 下沉（船体 y 线性下压，水花 + 气泡 + 油迹）
  ③ 乘员落水：转游泳态（`player` 或 `crewBot`），位置在水面
  ④ 残骸沉底：可作为水下掩体（复用 05b `sunkenWreck` 观感口径）
```
- **两栖车在水里 / 滩上被打爆**：与坦克一致走"燃烧残骸"分支，但不上浮——原地留残骸。

### 3.5 两栖车的水陆双态
| 态 | 触发 | 行为 |
|---|---|---|
| **履带态** | `waterDepthAt < 0.55` | 完全复用 `Tank` 的坡度物理 / `tankRideH` / OCC / 悬挂弹簧 |
| **浮航态** | `waterDepthAt ≥ 0.55` | 速度 ×0.45、转向迟滞 ×0.5、浪涌起伏、吃水平衡 |

## 五、Bot AI（三层）

### 5.1 `boatAI(craft, dt)` —— 艇智能体
状态机：`approach`（择湾进近）→ `patrol`（沿 `sea.navRing` 绕岛机动）→ `engage`（对岸压制）→ `evade`（弹着规避）→ `hunt`（追击对方小艇）
- **择湾**：四湾 `sea.lanes` 按"距本方集结点最近 + 岸防强度最低"评分。
- **规避**：落点预测（在途炮弹）→ 横向蛇形（`sin(nowT*0.8)*ampl`），ampl 随受威胁度上升。
- **鱼雷窗口**：目标舷角 ∈ [30°, 90°]、距离 ∈ [120, 600m]、提前量解算可达 ⇒ 发射。
- **对岸压制优先级**：反舰炮位 > 滩头工事 > 步兵集群。

### 5.2 `amphAI(craft, dt)` —— 两栖车智能体
- **涉水路线**：读 `waterDepthAt` 在礁盘上找 `≤0.40m` 的通道（礁盘平台 1.22m 太深 ⇒ 走**切深航道** `sea.channels` 或直接浮航）。
- **冲滩点**：四湾滩头两翼（`sea.lanes` ± 30m），用 `findClearSpot` 落位。
- **上岸后**：**零改动复用**现有 `tankPerceive / tankCoverPoint / pickTankTactic` 陆战层（`15-vehicles.js` 既定函数）。

### 5.3 `batteryAI(battery, dt)` —— 岸炮智能体
海面目标索敌 + 提前量 + 弹药节奏（与 `atGun` 的 Bot 节奏**同档数值源**，不另写一套）。

### 5.4 步兵反应
反坦克兵（`cls` 反装甲档）对水面载具的索敌扩展：`enemyTankNear()` 之后追加一次 `navalNear()` 扫描（火箭筒可打艇）。

## 十一之补 · 实施期裁定记录（Lead，2026-09-20 晚）

### 12.1 `tankWreck` 的"整塔翻倒在侧"—— 采用 wreck-art 的替代实现，**不加第二个碰撞盒**

**问题**：任务书要求"炮塔座圈错位或**整塔翻倒在侧**"，但硬约束②要求碰撞口径不变（车体实体盒 5.6×3.0）。几何上二者不相容：完整车体 + 一台横躺在车旁的炮塔（宽 2.4~2.9m）必然伸出 3.0m 宽的盒外 ⇒ 玩家可穿模；而给残骸加第二个碰撞盒会改 `BOXES` ⇒ **12 图布局指纹全部漂移**，直接违反红线 1。

**裁定：采纳 wreck-art 的实现**（绕 X 翻 180° **倒扣在车体后段甲板**上、再向一侧滚 0.18~0.30rad 压进车体、**炮管在座圈处折断落在车侧沙地**），并把这一取舍写进代码注释。
**理由**：①红线 1（零漂移）优先级高于单个造型细节；②"倒扣 + 炮管折断落地"同样是高辨识度的击毁形态，观感目标已达成；③新增碰撞盒会让残骸在滩头变成"两个独立硬掩体"，反而破坏既有的掩体口径与 `coverPoints` 语义。**取舍已记录，不是遗漏。**

### 12.2 沙箱桩保真度：`Object3D.userData`

**根因**：真实 three.js 的 `Object3D` 构造函数恒有 `this.userData={}`；`dev/verify-layouts.js:28` 的 `Obj3` 桩**漏了它**（全仓 30+ 个 dev 桩里只有它漏）。旧 `tankWreck` 不用 `userData`，直到本批引入零件标签才暴露 ⇒ stalingrad 布局构建抛 `TypeError`。

**修法（两条，互为保险）**：
1. **Lead** 给 `dev/verify-layouts.js` 的 `Obj3` 补上 `this.userData={};`（桩保真修复，纯增量）。
2. **wreck-art** 把零件标签从 `userData.wkPart` 改为**直挂属性** `m.wkPart` —— 对任何桩都安全，并把 `dev/verify-buildings.js`（同样缺 `userData` 的桩）一并带过。

**教训（写进后续批次纪律）**：dev 沙箱桩是"部分实现"，与真库的差异会**延迟暴露**（谁先在真实代码里用到某个真库恒有的字段，谁就踩）。新增桩字段时应以真库构造函数为准，而不是"够现有代码跑就行"。

### 12.3 反舰炮位落位距离

实测向陆距离：`SW 9.41m / SE 9.15m / NW 17.64m / NE 14.21m`（`inshore:16` 是起始值，`batteryPlace` 按 `shoreDist ≤ -8m` 逐档外推 + `findClearSpot` 重落位）。
**裁定：接受**。9.2~17.6m 全部在陆上、朝向向海（seaDot 1.000），且 `inshore` 的语义是"沿岬角法线从锚点向陆的**位移**"（实测 16~21m），而"到最近岸线的**距离**"在尖角沙嘴上必然更小（海岸绕着沙嘴包过来）—— 两种量，不是错位。滩头火力线的观感反而更好（离岸近 = 对海射界大）。
**补充断言（coastal-battery 新增，比"离岸 ≥12m"更贴合意图）**：炮位平台内切圆 `r=6.2m` 必须完全在陆上 ⇒ 炮位圈不压水线。四门全过。

### 12.4 ★ 方法论教训：实现者自检"直调内部 API"会系统性漏掉真链路缺陷

**实例（本批最重要的一个发现）**：`updatePlayerNaval` 的座位逻辑完全正确 —— 直接调 `tryInteract()` 时 `onNaval` 从 false 变 true。但玩家**在水上按 F 永远上不了艇**：`js/19-input.js:76-81` 的游泳分支
```js
if(player.swim){ /* 1/2/R */ return; }   // ← KeyF 在这里被 return 吞掉, 到不了 tryInteract()
```
实现者的自检之所以全绿，是因为它**直调座位 API**，绕过了真输入链（键盘事件 → 输入闸门 → 交互 → 座位）。**陆上路径正常**（`swim=false` 时不受该分支影响），所以只有"水上登艇"这一条真实路径断了 —— 而它恰好是用户裁定原文"**水上必须游泳贴近**"要保的那条。

**固化纪律（后续批次适用）**：任何"**玩家能否做到 X**"的断言，必须从**真实输入入口**走一遍（键盘/触控事件 → 闸门 → 交互 → 结果），不得从中间层直调。同理，任何"**画面上看不看得见 X**"的断言，必须用祖先感知的渲染判据（`dev/effective-visible.js`），不得只看元素自身 `display`。

**推论**：实现者的自检应当覆盖"我这条链路对内可用"（单元级），独立验证者的关卡必须覆盖"用户从零操作能达成"（端到端级）。两者的**入口不同**，不是重复。

### 12.5 端到端探针的靶件纪律

探针初版拿 `23-deploy` 生成的真载具当靶，结果它有 Bot 在驾驶、以 2.79m/s 漂移，判定前 2 帧就漂了 0.7m（实测 2.42m 仍拒上）。
**纪律**：端到端探针的靶件必须是**探针自建、`driverBot=null` 的静止实例**，否则测的是"追着动靶上船"，不是"上船"。同理试验场必须在**正确的介质**里（第一版把水上用例放在滩头陆上，`waterDepthAt` 返回陆上哨兵 `-1e9`，走了陆上 4.5m 分支 ⇒ 反向断言假失败）。

### 12.6 ★★ 本批最大的系统性风险源：**桩/替身的忠实度**

本批一共踩了**四例**同一性质的坑，形态是"辅助设施与真实现不同源"：

| # | 现象 | 桩的偏差 | 后果 | 谁抓到 |
|---|---|---|---|---|
| 1 | `m.userData.wkPart` 抛 TypeError | `dev/verify-layouts.js` 的 `Obj3` 缺 `Object3D.userData`（真库恒有） | **假故障**：stalingrad 布局构建崩 | Lead |
| 2 | `atGun` A/B "漂移" | A/B 未钉 `Math.random`（`findClearSpot` 走 `rand()` 而非 `_wstate`） | **假故障**：报出并不存在的陆战漂移 | verifier 自查 |
| 3 | `08-effects.js:366` 抛 TypeError（songhu） | `_bootstub.js` 的 `InstancedMesh.setMatrixAt` 用 `{}` **覆盖** `instanceMatrix`（真库是写入 `.array`） | **假故障**：报出并不存在的下沉链缺陷 | wreck-art + Lead |
| 4 | **海战 AI 全程往外海开、两栖车永不上岸** | naval-ai 沙箱替身写 `yaw += turn*rate*dt`，而真 `15d-naval.js:284` 是 `yaw -= turn*…*dt` ⇒ **替身与实现同源错误** | ★**假绿**：一个真实的高影响缺陷(舵向反打)被自检判为 PASS | verifier + naval-hull 对质 |

**固化纪律（后续批次必须遵守）**：
1. **替身/桩的每一处行为，必须逐字对照真实现的源码行**，不能凭"应该是这样"写。naval-ai 修法：替身改成与 `15d:284` 逐字同口径。
2. **凡是"我在沙箱里证明了 X 成立"的结论，必须再有一条"从真实入口走一遍"的独立证据**（本批两栖车上岸的真相就是被 verifier 的真浏览器/独立夹具 + naval-hull 的 `NAVAL_AI_DIAG` 轨迹夹出来的）。
3. **报 FAIL 前先看阳性对照**（本批 wreck-art 的 A⑦ 阳性对照是这条纪律的一个正面样板）。
4. 桩字段一律以**真库构造函数**为准（`Object3D.userData` / `InstancedMesh.instanceMatrix.array` 都是恒有字段）。

### 12.7 舵向符号缺陷（红线 7）的最终定案

**根因**：`js/15d-naval.js:284` `this.yaw -= this.inTurn*S.turn*turnMul*dt*(this.inFwd<0?-1:1)` ⇒ **`turn=+1` 是右转（yaw 减小）**。而 `14-bots.js` 的 `navSteer` 喂 `+angDiff(c.yaw,want)`（假定 `turn=+1` 使 yaw 增大）⇒ **舵反打** ⇒ 航向误差被正反馈放大到饱和 ⇒ 艇/两栖车绕圈往外驶，`amphAI` 的 `mode` 恒停在 `approach`、永不进上岸层。

**A/B（同一夹具，只改一行符号）**：

| 用例 | 修前 | 修后 |
|---|---|---|
| 艇 @muster(0,250) | minShore=**-4.2m（开上陆地）**、搁浅 2291/4200 | minShore=73.9m、**搁浅 0** |
| 两栖车 @muster | 未上岸、0 开火 | **上岸 39.6s、开火 8 次** |
| 艇 @`[0,-250]` | minShore=2.0m、搁浅 1955 | minShore=**38.2m**、搁浅 **0**、tReach **11.2s** |
| 两栖车 @`[0,-250]` | 未上岸、0 开火 | **上岸 51.6s、开火 3 次** |

**修法**：`navSteer` 与 `navLandSteer` 统一 `clamp(-angDiff(c.yaw,want)*1.6,-1,1)`，并在注释里写明"**符号换算只在这一层做一次，全段其余地方只用 yaw**"；`drive()` 的 4 个调用点全部复查无第二处漏改。`js/14-bots.js` md5 前 8 = `52cdef39`。

**连带修复（coastal-battery 实报 + naval-ai 自查出的同类第三处）**：
- `navScanShore` 的 `batteryNear(x,z,r)` **未传队别** ⇒ 日军艇把自家岸炮当压制目标开火（友军火力）；
- 同类第三处：`navShoreDef`（择湾的"岸防强度"评分）也把自家炮位算作岸防 ⇒ 会污染择湾评分。
- 滩头工事补队别过滤（MG42S 有 `team`、MORTARS 有 `owner.team`；`ATGUNS` 无队别字段，按中立工事处理）。
- **回归断言**：起点 (-235,70)（最近日军炮位 SW 115.9m，在射程内 ⇒ 排除假阴性）→ **日军艇索敌自家炮位 0/1800 帧**，美军艇索敌日军炮位 **1799/1800 帧**（正对照，证明过滤器没有过度屏蔽）。

**被否决的接口扩张**：naval-hull 提议给 15d 加只读快照 `craft.depthAhead`（艏向前方 12m 水深）供 AI 提前转向 —— naval-ai 复核后**否决**：艇的转向半径 ≈ `v/ω` ≈ 23m，**12m 探针短于一个转向半径，来不及提前转**。改用他已有的 `navAheadDepth`（25/50m 双探针）+ `<36m 向海外转` + `≥105m` 压制站位，修后实测 **0 搁浅**。**15d 的冻结接口保持不变。** 这条记录的价值在于：**一个看起来合理的接口建议，被"数字对不上物理"驳回了** —— 比"先加了再说"更省。

### 11.9 开工后追加的裁定（2026-09-20 晚，覆盖前面未写到的细节）

**① 波场单源** —— `00-config.js` 已新增：
```js
function seaWaveOffset(x,z,t)   // = sin(t*waveFreq + x*waveKx + z*waveKz) * waveAmp
```
`15d-naval.js`（载具）与 `05b-props.js` 的 `updateBuoys`（浮标）**必须同调这一支**。
- 为什么不能用随机相位：原 `BUOYS` 用 `ph:wr(0,TAU)` 的随机相位，"艇与浮标同波"在数学上不可能成立。
- ★ `buoy()` 里的 `ph:wr(0,TAU)` **取数必须保留**（`wreck-art` 实测：删掉它会改变 `05-world` 的全局确定性随机流 `_wstate`，直接把布局指纹打漂）。该值不再参与浪涌计算，只作保留取数，需加注释说明。

**② 单一驱动点 + 帧戳幂等** —— `boatAI/amphAI` **必须自带帧戳去重**：
```js
function boatAI(craft,dt){ if(craft.__aiTick===nowT) return; craft.__aiTick=nowT; ... }
```
于是"15d 的 `update()` 里调用"与"naval-ai 在 `Bot.update` 首行的兜底钩"可以共存而**不会双跑**（双驱动 = 双倍速度，是硬故障）。物理与 AI 的先后仍以 `updateNaval` 为准。

**③ 玩家/载具接口追加字段（`naval-model` 提供，纯增量）**
