## 1. 冻结级三连

### 1.1 ① `NAV.refresh()` 全量重烘焙 —— 胡康 1177ms → 11ms

**原状**：`NAV.refresh()` = `buildOccupancy()` + `buildSpatialIndex()` + `bakeGrid()` + `bakeComponents()`，
四步全是**整图**量级。触发点却清一色是局部事件，且**反复触发**：
火焰蔓延期 `fireNavT` 每 5s 一次（`04b-fire`）、每次墙体/结构崩塌（`05-world`）、每次工程兵建造
（`06-engineering`）、每次铁丝网被碾平（`15-vehicles`）。

**分阶段实测**（`dev/_navstage.js`，改动前）：

| 图 | NAV.refresh | 其中 buildOccupancy | 其中 烘边+分量 |
|---|---|---|---|
| 胡康河谷 640 | **1177 ms** | **1044 ms** | 128 ms |
| 断崖公路 320 | 726 ms | 689 ms | 21 ms |
| 塔拉瓦 640 | 577 ms | 501 ms | 73 ms |
| 莫斯科 640 | 302 ms | 165 ms | 132 ms |
| 淞沪 320 | 291 ms | 243 ms | 30 ms |
| 百团 640 | 254 ms | 124 ms | 125 ms |

即：**主犯是 `buildOccupancy` 里那几支"逐格全场扫描"的判据**（胡康逐格 `inRiverChannel` 463k 次、
塔拉瓦逐格 `seaDepthAt`+`onBridge`、断崖逐格 `heightAt+roadDist`、莫斯科逐格 4×`heightAt`），
它们**只读地图静态几何**，一局之内恒定。

**改法两条**（缺一不可）：

1. **静态地貌层缓存**（`03-terrain buildOccGeo`）：河道深谷带 / 深水海面 / 断崖岩脊 / 雪岭陡坡，
   以及百团沟壁与雾林谷壁的 4m 步进厚墙扫描（`buildWallMask`），惰性算一次存字节掩码；
   之后每次重建只做"读掩码→写占用"的紧循环。语句位置、叠加顺序、取值与旧版逐条对齐
   （含"后写覆盖先写"与"莫斯科那一支旧版就挂在 `if(campaign==='moscow')` 内"的作用域）。
2. **增量重烘焙**（`07-nav`）：脏矩形由 OCC 侧给出 —— `occDiffRect` 逐格差分（**差分为空 ⇒ 导航输入逐格未变
   ⇒ 整段跳过**，这是证明式跳过不是估计）+ `occTouch` 补记 4 处"绕过 buildOccupancy 直接写 OCC"的路径
   （`registerDynCollider` / `killDynCollider` / `05-world killOne` / `04b-fire occMarkFire`）。
   NAV 侧只重算脏范围外扩 2 格的 `open`、外扩 1 格的四张边表，并只对被波及的连通分量重标
   （`bfsFill` 与全量烘焙**共用同一段**，避免判据漂移）；脏矩形超过 `NN×4%` 时自动退回全量。

**实测（改后）**：

| 图 | NAV.refresh | buildOccupancy |
|---|---|---|
| 胡康河谷 | **11 ms** | 6 ms |
| 莫斯科 | 17 ms | 9 ms |
| 柏林 | 8 ms | 3 ms |
| 塔拉瓦 | 7 ms | 6 ms |
| 雾林 | 7 ms | 5 ms |
| 淞沪 | 5 ms | 1 ms |
| 草原 | 4 ms | 1 ms |
| 断崖公路 | **1 ms** | 0 ms |

**局部改动实测**（`dev/_navincr.js`，胡康）：

| 场景 | 增量 refresh | 全量 refresh | 提速 |
|---|---|---|---|
| 无改动 | 0 ms（跳过） | 137 ms | 17× |
| 塌一堵墙 | 2 ms | 134 ms | 8× |

**等价性判据**（同脚本，每场景"增量 vs 强制全量"逐格比对）：
`open` / `eH` / `eV` / `eD1` / `eD2` **逐格相同**，连通分量**划分相同**（编号可能不同 ⇒ 用

**11 张图 × 8 场景 = 88 组比对全绿，0 处不一致。**

### 1.2 ② 桥梁一行让四张图的高度快路归零 —— `heightAt` 12~14µs → 2.96µs

**原状**：`03-terrain hgridClear()` 末尾一行

```js
if(BRIDGES.length) m=-1; // 桥面抬升带 (noBridge 双语义共存): 恒走精修
```

只要图上有桥（胡康 2 座 / 淞沪 2 座 / 百团 1 座 / 塔拉瓦栈桥），**全图每一格**都被判"带内"，
`heightAt` 的 HGRID 快路命中率恒为 0。而 `heightAt` 是全库热点：射线、LOS、寻路、坦克足印、
布娃娃落地、坡度物理、站立高度全走它。

**改法**：桥面抬升本来就**只在桥矩形内生效**（`onBridge` 的 `|ax|<len/2 && |pv|<w/2`），
矩形外逐位等于不带桥的结果 ⇒ 带外格可以安全走快路。改为按**桥矩形到格心的距离**记账
（轴系变换 + 外廓距离，与 PADS 支同一套算法），只有距离 < `PAD`(2.2m) 的格才判带内。
两种 `noBridge` 取值也随之自动正确（带外两义同值 `rawHeight`，带内格照旧走精修分支）。

**顺带查出并修掉的第二个洞**：PADS 支沿用 `padHeight` 的 `dx²+dz²>p.reach2 ⇒ continue` 提前跳过 ——
但 `padHeight` 是**逐点**判定，`hgridClear` 只能拿**格心**代表整格；`reach2` 是"矩形外接圆+ramp"的半径，
**格心落在圆外、格内某点仍在裙坡带里**的情形确实存在（矩形角落方向：到矩形与到中心的距离不是一回事）——
那一格因此丢掉整个平台项，快路把带裙坡的地形当成裸地形（柏林实测差 **2.5e-4 m**）。去掉提前跳过即可
（PADS 条目数十量级，且本函数惰性缓存、每格只算一次）。

**实测（改后，`dev/_perfprobe.js`）**：

| 图 | heightAt | 快路命中率 | 400m 眼位射线 |
|---|---|---|---|
| 胡康河谷 | **2.96 µs**（前 12~14） | **92.0%**（前 0%） | **0.115 ms**（前 0.7） |
| 莫斯科 | 2.62 µs | 86.5% | 0.055 ms |
| 断崖公路 | 5.31 µs | 95.5% | 0.090 ms |
| 塔拉瓦 | 7.91 µs | 89.5% | 0.35~0.5 ms（见 §7.2） |

**等价性判据**（新增 `dev/_equiv-hgrid.js`）：11 张图 × 20k~40k 采样点（一半均匀随机、一半贴特征：
FLATS/PADS/河道折线/桥缘/壕沟/旗点/基地/出生点）× 三种口径（快路开 / 快路关 / `noBridge=true`）
**逐位一致 0 处**（合计 232,901 点）。这条判据同时是"快路判据不得漏登记特征"的常驻护栏。

### 1.3 ③ `raycastWorld` 的地形推进 —— 不改采样口径（根因已由 ② 消掉）

**原状**：`dir.y<0.35` 时按固定 `step=1.8m` 推进 + 6 次二分，近水平射线在 400m 上要 222 次 `heightAt`。

**结论**：**不动**。理由三条：
1. 每次 `heightAt` 的成本才是根因，② 已把它从 12~14µs 降到 ~3µs（胡康 400m 射线 **0.7 → 0.115 ms**）。
2. 1.8m 步长 + 6 次二分是**本仓定义的"子弹打在地形上"语义**（弹着点/扬尘位置都由它决定）。
   改步长会改变可见的弹着位置，属行为变更，而沙箱无法验证观感。
3. 高程场没有加速结构（无 min-max mipmap），222 次采样是"无索引高度场射线"的固有代价；
   真正值得做的是给地形建层次包围，那是另一个量级的工程。

### 2.1 ④ 每帧对象 churn（三处热点）

| 位置 | 旧版 | 频率 | 改法 |
|---|---|---|---|

### 2.2 ⑤ `updateHUD` 写入去重 —— 稳态每帧 ~30 次 DOM 写入 → 0 次

**原状**：每帧无条件写 `hpNum.textContent` / `hpBar.style.width+background` / `stamBar.style.width` /
`vehHpWrap.style.display` / `wname`·`wmode`·`magN`·`resN`·`nadeN` / `capPanel`·`capTxt`·`capBarFill` /
`dmgOv`·`lowOv`·`supOv`.opacity / `nadeWarn` / `leadPip`·`tankPip`·`mgPip` / `braceInd` / `crosshair`…
其中**绝大多数帧的值与上一帧完全相同**（血量没掉、没在载具上、没举准星）。
浏览器对"写同一个值"仍要走 CSSOM 与样式失效判定，60fps × 二三十处是白开的样式重算；
`nadeN` 那条还要每帧拼 4~6 个字符串。

**改法**：`hudText` / `hudHTML` / `hudClass` / `hudStyle` / `hudShow` 五个包装，值相同即整段跳过；
**自定义属性走 `setProperty`**（`style['--gap']=…` 是无效写法，会被静默丢弃 —— 准星张开量正是这条路）。
只在"该字段写点唯一"处使用：逐项 grep 核过这些 id 在 22-hud 之外无第二写点
（`nadeWarnT`/`streakBuff`/`dmgFlash` 等只是被读的状态量）。

**判据**（新增 `dev/_hudwrite.js`，28 项）：
- **稳态 6 帧每帧路径实际 DOM 写入 = 0 次**（10Hz 低频块按设计仍 10Hz 重画，不计入）
- 逐项改状态后 DOM 必须立刻反映：掉血/低血档配色/体力/架枪三态/手雷警告/受击闪屏/压制遮罩/
  准星 `--gap`（经 `setProperty`，计数 >0）/开镜隐藏/上下载具/连杀角标（display+className+innerHTML）/到期收起
- 200 帧状态抖动下 `updateHUD` 零异常

## 3. 渲染端复核（⑥⑦⑨：复核后不改，理由如下）

### 3.1 ⑥ 阴影与实例批 —— **"上万个 draw call"的归因是错的**

复核后的三点事实：
1. **`autoUpdate` 不能关**：太阳阴影锥每帧跟随相机（`updateSunShadow` 按纹素对齐），场景里
   士兵/载具/碎块/粒子全是动态物体 ⇒ 阴影贴图每帧都必须重画。
2. **实例批不是 draw call 洪水的来源**：`trunks`/`leaves`/`BUSH_IM` 是**一个** InstancedMesh
   = **1 个 draw call**（阴影 pass 里树干那 1 个）。`frustumCulled=false` 的真实代价是
   "顶点量恒被处理"，不是 draw call 数；对 2000 棵树 × ~50 三角形 = 10 万三角形，现代 GPU 上是 0.1ms 级。
3. **真正的 draw call 量来自逐件 mesh**：塔拉瓦 7710 个网格里有 ~5400 个属于 **386 个棕榈 Group**
   （每株 1 干 + 8~10 叶 + 3~5 果 ≈ 14 个 mesh）。这是**内容管线**问题（该用实例批/合批），
   不是配置问题 —— 见 §7.3 的处置建议。

### 3.2 ⑦ 距离剔除 / LOD / `camera.far`

`camera.far=900` 与**天空球半径 760**（`SphereGeometry(760,…)`，跟随相机）以及**太阳贴片**
（`(-380,480,170)`，固定世界坐标、玩家最远可到 ~1080m 外）绑在一起 —— 缩 `far` 会切掉天空与太阳，
是**可见的视觉回归**，而沙箱（无 WebGL）无法验证。LOD 方面士兵/载具已有 AI LOD
（`tickSkip` 按 60m/110m 分 1/2/3 档），远处坦克仍有完整更新（`for(const t of tanks) t.update(dt)`）——
要给载具加 LOD 是行为变更（炮塔/履带/悬挂的表现），本轮不做。

### 3.3 ⑨ 画质档位 —— **复核订正：原判断部分不成立**

原清单说"质量档位救不了正在进行的对局"。复核代码后：`22-hud:1208` 的画质按钮
**点击即调 `applyQuality()`**，而 `applyQuality()` 改的是**当场生效**的四项：
`setPixelRatio` / `sun.shadow.mapSize`（并 dispose 旧贴图）/ `shadowMap.type`（PCF ↔ PCFSoft）/
`scene.fog.far`（并连带 `sun.shadow.camera` 视锥与 CSS 滤镜）。粒子数量也是**生成时**读 `SETTINGS.quality`。
真正冻结的只有两项，且都是设计使然：`antialias`（渲染器构造期固定）与植被密度（世界构建期固定）。
**唯一可议之处**是入口位置：画质按钮在主菜单的"游戏设置"里，对局中要先「返回主界面」再进设置
（战局会冻结不丢）。这是 UX 取舍，不是性能缺陷；改暂停面板布局属可见 UI 变更，本轮不动。

## 4. 物理 / 冗余 / 回收

### 4.1 ⑧ 逐实例材质 → 模块级共享

`05b-props` 里四处**逐实例** `new THREE.MeshLambertMaterial({color:…})`：棕榈果（塔拉瓦 386 株 × 3~5 果
≈ **1500 个**）、竹杆（胡康 ~1000 根）、雷区警示桩、弹坑土埂。按颜色提到模块级共享
（`MAT_PALM_NUT` / `MAT_BAMBOO` / `MAT_MARK_RED` / `MAT_CRATER_RIM`）。

**为什么可以安全共享**：全库 `grep` 过 `material.color/opacity/emissive/map/transparent` —— **零处写点**
（无任何按实例改材质的地方）⇒ 同色同类型的材质合并后**渲染结果逐像素相同**，但省掉上千个材质对象，
并让渲染器的"连续同材质"判定生效（相邻 draw call 不再重复上传 uniforms / 切状态）。

**顺带核验（都没问题，不改）**：棕榈叶的 `boxGeo(0.46,len,0.09)` **本就按尺寸缓存**
（`05-world boxGeo` 的 `_geoCache`，随机长度经 `toFixed(2)` 后只剩 ~120 个键）；
弹坑用的是共享 `craterGeo`/`craterMat` 且运行期弹坑有 **36 个上限**（`runtimeCraters.shift()`）。

### 4.2 ⑬ RGRID 去重戳按需扩容

`RGRID.stampB` 只在 `buildSpatialIndex()` 时按"当时盒子数 +96"定容，而 `addBoxCollider` 运行期
还会持续追加（工程兵建造 / 残骸 / 探针摆件）——**越出容量的下标在 TypedArray 上静默读成 `undefined`**，
于是"本代已测过"的去重失效：同一盒在其覆盖的每个栅格里被重复测试。
现改为 `raycastWorld` 入口按需扩容（一次长度比较；`RGRID.gen` 单调递增，换新数组后全 0 的旧代值
不可能等于当代 gen ⇒ 无"误判已测"的风险）。
（附注：`eachBoxNear` 对越界下标是**跳过去重直接回调**，大盒跨多格时会把同一盒回调多次 ⇒
推挤重复施加；当前建造件都 < 13m 一格，不可达，但同一处扩容已把它一并堵上。）

### 4.3 ⑩ 广相：**实测驳回**

用真 cannon 0.6.2 复刻游戏刚体规模（8 具布娃娃 × 9 体 + 96 碎块 + 地面 = 170 刚体，`dev/_broadphase.js`）：

| 广相 | 活跃期 | 静置期（热身 600 步后） |
|---|---|---|
| `NaiveBroadphase`（现状） | 2.38 ms/步 | **2.373 ms/步** |
| `SAPBroadphase` | 1.95 ms/步 | 2.316 ms/步 |

- **提速只有 1.02×（静置）/ 1.22×（活跃）** —— 不值得为它冒险。
- 更关键：同步数后各刚体位置差 **平均 1.52 m / 最大 11.66 m，159/169 具偏差 >5cm** ⇒
  cannon 0.6.2 的 SAP 会**改变实际物理结果**（布娃娃落姿、碎块堆积），是可感知的行为变更。
- 另记一笔（本轮不做）：170 刚体**静置期仍 2.37ms/步** —— cannon 默认不睡（`allowSleep=false`）。
  要省这笔得开 `allowSleep` 并在**每一处**给刚体施加冲量的地方补 `wakeUp()`
  （爆炸/坦克推挤/子弹击飞散在多个文件），漏一处就是"尸体不吃爆炸"，属行为变更。

### 4.4 ⑭ 音频：不改

每次枪声 ~19 个节点是**程序化合成器**的设计（每发独立的包络/滤波/回声）。现有两道闸门方向正确：
远场 `dist>70` → 100ms 窗口最多 4 发；**不可闻早退 `sp.gain<0.025` 发生在建节点之前**（远距离交火不产生节点）。
近场再叠一道"每帧节点预算"会**听得见地**丢枪声，而沙箱没有 WebAudio 渲染（桩只记录调用），
无法验证听感 —— 属"改了可能更坏"的一类，不动。

## 7. 修完之后的自审（"确保不会越修越坏"）

### 7.1 复查发现并补掉的一个真漏洞：脏矩形累积

第一版实现里，`buildOccupancy` 每次都用**覆盖式**写 `OCC.dirty`（= 与上一次重建网格的差分 ∪ 直接写范围）。
复查时发现一个反例：**若两次 `buildOccupancy` 之间没有 `NAV.refresh`**（世界构建期 `06-engineering`
就是连调两次），第二次重建的差分基线是第一次的产物 —— 若两次结果相同，差分恒为空，
于是**"第一次相对已烘焙状态的改动"被丢掉 ⇒ 导航永远停在旧状态**。

**修法**：脏矩形改为**累积**（`union(旧脏, 新差分, 直接写范围)`），只有 `NAV.refresh` 消费后
才由 `occDirtyClear()` 清账（唯一清账点）。这样无论中间重建几次，改动集都不会漏；
代价只是"清账前多算几格"。
★**改完重跑** `_navincr`（11 图 × 8 场景 = 88 组全绿）+ `run-all-verify`（21/21）确认。

### 7.2 复核中查明的两件事（原清单归因不准，据实订正）

1. **塔拉瓦的射线成本不在高度场**：400m 射线 0.35~0.5ms，但其中 `heightAt` 只占 **7 次**
   （射线在 10m 内就打到滩头障碍，地形推进提前收敛）。真实开销在 **box 候选表**：
   单条 60m 射线就要过 **354 个盒**，全图最密的 13m 格里有 **327 个盒**（@ 92,-129 登陆滩）。
   `rayBox` 裸成本实测 98 ns/次。⇒ 这是 **RGRID 13m 格在密集障碍区的粒度问题**，
   不在本批 14 条内，单独列出待裁定（改格距会影响内存与 `buildSpatialIndex` 耗时，且属全局参数）。
2. **实例批 `frustumCulled=false` 的代价被高估**：它是 1 个 draw call、10 万三角形量级，
   不是 draw call 洪水（见 §3.1）。

### 7.3 复核查明的第三件事：`verify-nav` 偶发失败的根因在**输入侧**（世界构建不可复现）

全量套件第二次跑出现 `verify-nav-20260926` 偶发失败（✓5 / ✗1），而该套件自带"失败项连跑 3 次"的稳定性复核
给出 0/0/0（三次全过）⇒ 判为偶发。我据此做了两项取证：

1. **连跑 14 次未复现**（全部 ✓6/✗0），失败率 <1/20。
2. **根因定位（决定性）**：新增 `dev/_seeddet.js` —— 同一 `?seed=42` 下**独立 boot 两次**，
   比对占用格数 / 逐格哈希 / BOXES / CYLS：

   | 图 | 第一次 | 第二次 | 结论 |
   |---|---|---|---|
   | 草原遭遇 | 占用 8709 / BOXES **3053** | 占用 8682 / BOXES **3047** | 不可复现 |
   | 诺曼底 | 占用 10491 | 占用 10529 | 不可复现 |
   | 胡康河谷 | 占用 35238 | 占用 35230 | 不可复现 |

   ⇒ **世界构建在同一 seed 下仍不可复现**（`BOXES` 数量都不一样）。来源是布局期仍有
   `Math.random` 路径：`06-engineering` 的机枪落位 `mgSpot()` 用 `rand(-spread,spread)` 探位
   （`rand` = `Math.random`，而布局期其余随机走的是可播种的 `wr`），机枪沙袋墙是真实碰撞盒 ——
   草原 BOXES 两次差 6 个，正好是一处机枪掩体的沙袋数。

**结论**：任何"按布局断言导航/占用/植被结果"的探针都是**在随机输入上做确定性断言**，偶发失败是探针设计的固有问题，
**与本批改动无关**（我这边有独立证明：增量 ≡ 全量在 **11 图 × 8 场景 = 88 组**逐格全绿，
且首次烘焙是走同一支 `bfsFill` 的全量烘焙）。

**收尾复跑出现的第二个偶发**：同一批的 `_audit-foliage-ref`（植被遮蔽独立审计，**本批未碰植被代码**）
也偶发 1 次（✓5/✗1 → 稳定性复核 0/0/0 三次全过；我另外连跑 8 次全绿）。该探针把生产
`foliageBlocksLOS` 与一份**独立参考实现**逐段对照，判据落在"灌木/蕨/树/棕榈遮蔽带"的边界上 ——
随机布景偶尔会造出正好压在带边界的样本。**两个不同探针在不同轮次各偶发一次**，
与"输入不可复现"这一根因一致。
**待办（留给裁定）**：要彻底消除这类偶发，需让布局期随机**全部**走 `wr`（见下），
或给这两个探针加"固定若干种子重试取多数"的判据。
**为什么不顺手修**：把 `mgSpot` 的 `rand` 换成 `wr` 会**消耗可播种随机流** ⇒ 后续所有 `wr` 取值整体位移
⇒ 各图布局全变、`verify-layouts` 的指纹（fp=311147）随之失效。这是"验证可复现性"与"布局指纹基线"的取舍，
属**需要用户裁定的口径变更**，不在本轮擅动。
**变通**：套件已内置"失败项连跑 3 次"复核，会把这类偶发单独标成"偶发"而不计入失败。

### 7.4 留待裁定的三项（本批**未**动，理由均为"可见行为变更且沙箱无法验证"）

| 项 | 现象 | 为什么不动 |
|---|---|---|
| 棕榈逐件 mesh（塔拉瓦 ~5400 格） | 386 株棕榈 ≈ 塔拉瓦全部网格的 70% | 要改成实例批得重构 `floraHashAdd({meshes:[grp]})` 的整株隐藏/燃烧/还原链路（04b-fire / 23b），风险高 |
| 170 刚体静置期 2.37ms/步 | cannon 默认不睡 | 开 `allowSleep` 需逐处补 `wakeUp()`（爆炸冲量打在睡眠刚体上会被丢弃） |
| RGRID 13m 格距 | 密集区单格 327 个盒 | 全局参数：改小 ⇒ 内存与建索引耗时上升；改大 ⇒ 射线/碰撞候选变多 |
